### Multi-object and re-identification after occlusion
- SAM 2-family trackers keep a per-object FIFO memory of recent frames plus prompted frames and object pointers, and predict an object-presence/occlusion score each frame (exposed as `object_score_logits` in transformers). This handles short occlusions and re-acquires when the object reappears inside the memory window, but a fixed window "indiscriminately retains past frames", causing drift and ID switches in clutter (the failure mode SAMURAI/DAM4SAM/SAM2Long fix). Sources: [SAM 2 paper](https://arxiv.org/abs/2408.00714), [survey of SAM2 trackers on FMOX](https://arxiv.org/pdf/2512.09633).
- Cost scales per tracked object (the image encoder is shared, memory attention is not); EdgeTAM's contribution is precisely making memory attention cheap. Keep the active set small (objects near a hand, section 7).
- For long absences (object leaves the room), no memory tracker will re-ID on its own. SAM 3's recipe is the right one to copy at pipeline level: **periodic detector re-prompting** (high-confidence detections replace tracker masks so "the memory bank has recent and reliable references"), a **detection-consistency score** that suppresses masklets not matched by detections over a window, and spawning new masklets for unmatched detections ([SAM 3 paper, video section](https://arxiv.org/html/2511.16719)). Add an appearance embedding per track (MobileCLIP2-S0 image encoder, 1.5 ms on iPhone 12 Pro Max, [ml-mobileclip](https://github.com/apple/ml-mobileclip)) to re-link identities after long gaps.

### Integration caveats
- All of these run internally at 1024² (SAM 3 at 1008); for 480p you are paying for upsampling. Test reduced internal resolution (512/768) with interpolated position embeddings; sam2-mlx exposes the internal resolution.
- Apple's Core ML SAM 2.1 is image-only; the Core ML video path today is EdgeTAM's own exporter. MLX is the least-friction video path with measured numbers.
- Torch-MPS has fp16 regressions on M4 ([Apple forum thread](https://developer.apple.com/forums/thread/778692)); prefer MLX or Core ML for the per-frame model.

Streaming video-LLM literature, and what it tells you:
- [VideoLLM-online (CVPR 2024)](https://arxiv.org/abs/2406.11816): 7B, 10–15 fps on an A100 only with an async encode/decode pipeline. [Flash-VStream (ICCV 2025)](https://github.com/IVGSZ/Flash-VStream): STAR memory, 7B. [Dispider (CVPR 2025)](https://arxiv.org/pdf/2501.03218): 1 fps, 7B. [TimeChat-Online (ACM MM 2025)](https://arxiv.org/abs/2504.17343): Differential Token Drop removes 82.8% of tokens at 98% of StreamingBench accuracy — "80% of visual tokens are naturally redundant". [StreamingVLM (Oct 2025)](https://arxiv.org/abs/2510.09608): 8 fps on one H100, stable for 3 h with a compact KV cache. [Event-VStream (Jan 2026)](https://arxiv.org/pdf/2601.15655): decode only at motion-semantic event boundaries. [ViCoStream (Jun 2026)](https://arxiv.org/html/2606.19849v1): 134 fps throughput on an A100 via stage-wise coordination.
- Offline temporal grounding (Charades-STA R1@0.5, from [Time-R1](https://arxiv.org/html/2503.13377v2) Table 1): TimeChat 32.2, VTimeLLM 27.5, TRACE 40.3, VideoChat-Flash 53.1, HawkEye (FT) 58.3, TimeSuite (FT, 349K examples) 67.1, **Time-R1-7B 60.8 zero-shot / 72.2 fine-tuned with only 2.5K RL samples**. [TimeLens (Dec 2025)](https://arxiv.org/html/2512.14698): the three things that matter are (1) interleaved textual timestamps, (2) thinking-free RL with verifiable IoU rewards beats SFT, (3) benchmark labels are noisy (TimeLens-8B: 63.0 R1@0.5 / 55.2 mIoU on the cleaned set).

What actually works at 2–4B: keep the VLM out of the detection/tracking loop entirely. Perception cuts a 2–4 s clip around a candidate event (contact start/end, lift, articulation), the VLM receives 6–8 timestamped frames plus the crop and answers a constrained question ("Did the person pick up the mug? yes / no / cannot tell") with a forced abstain option. If you fine-tune, do GRPO-style RLVR with an IoU/accuracy reward on a few thousand clips (Time-R1 recipe), not LoRA-SFT on JSON. Expect ~0.5–1 s per verification for Qwen3-VL-4B 4-bit on an M4/M5 Max with cached frame prefixes [est. from the measured 9.4 s / 32 frames].

## 7. Proposed real-time pipeline (480p, camera 30 fps, processing 15 fps)

Lanes run concurrently: ANE (Core ML), GPU (MLX/MPS), CPU. Budget per processed frame = 66.7 ms.

| Stage | Model / path | Rate | Cost per call | Amortized per processed frame | Lane |
|---|---|---|---|---|---|
| Ingest + decode + motion gate (frame diff / `VNGenerateOpticalFlowRequest` low-res) | VideoToolbox + CPU | 15 fps | ~2 ms | 2 ms | CPU |
| Hand pose | Vision `VNDetectHumanHandPoseRequest`, max 2 hands | 15 fps | ~8–12 ms [est. from "video-rate"] | 10 ms | ANE |
| Open-vocab detector | YOLOE-26s Core ML @640 (or OmDet-Turbo-Tiny) | 5 Hz + on demand when a hand appears/contact ends | ~10–15 ms [est. from YOLO26s 57.7 fps on M4 Pro] | 5 ms | ANE (or GPU) |
| Memory tracker for active objects (≤4, those near a hand or recently touched) | EdgeTAM (Core ML/MLX) at 512–768 internal res; DAM4SAM-style memory rules; detector re-prompt every 1 s | 15 fps | 25–40 ms [est. from 16 fps @1024² on iPhone 15 Pro Max; SAM2.1-tiny MLX 71 ms on M2 Max] | 30 ms | GPU |
| Depth | Depth Anything V2-Small Core ML | 5 Hz (15 Hz during a lift candidate) | 25 ms [measured M3 Max] | 8 ms | ANE |
| Contact state | Hands23 on hand ROIs (or keypoint∩mask geometry only) | 2–3 Hz, only while a hand is within 1.5× object size | ~100–150 ms [est.] | 20 ms | GPU (background) |
| Interaction classifier on the track clip | X3D-S (or VideoMAE-S) on 16-frame 224² object-centric crop | event-triggered (a few per minute) | ~5–10 ms (X3D-S) / 20–50 ms (VideoMAE-S) [est.] | <2 ms | GPU |
| Event verifier | Qwen3-VL-4B 4-bit, 6–8 timestamped frames | event-triggered | 0.5–3 s | off critical path | GPU, idle slots |
| Appearance re-ID | MobileCLIP2-S0 crop embedding | on new/lost tracks | ~2 ms | <1 ms | ANE |

Critical path: GPU lane ≈ 30 (tracker) + 2 (classifier) + ~5 (detector if scheduled on GPU) ≈ **37–45 ms** → 15 fps with ~20 ms headroom; ANE lane ≈ 10 + 5 + 8 ≈ 23 ms; CPU ≈ 5 ms. Worst case (4 active objects + Hands23 call + VLM prefill contending for the GPU) ≈ 60–90 ms; degrade gracefully by dropping the tracker to 7.5 fps for that window rather than stalling. If measurements on the M4/M5 Max come in at ≤25 ms for EdgeTAM, the same layout runs at 30 fps.

Memory: EdgeTAM + YOLOE-26s + DA-V2-S + MobileCLIP2-S0 < 300 MB; Hands23 ≈ 0.5 GB; Qwen3-VL-4B 4-bit ≈ 3 GB; optional SAM 3.1 MLX 3.5 GB. Well inside 48 GB; the constraint is GPU time, not RAM.

Event state machine (per track), which is where abstention comes from:
idle → approached (hand within d) → contact (keypoints inside mask ≥ N frames; Hands23 "hold" confirms) → lifted (mask depth departs support plane and centroid rises) → carried (mask moves with the hand) → placed (contact ends, mask stationary ≥ M frames). Open/close: articulated object track + classifier on the clip. Emit "unknown" whenever the tracker's presence score is low, detector and tracker disagree for > 1 s, or the VLM answers "cannot tell". This replaces both the CSRT failure mode (appearance change) and the VLM failure mode (no abstention).

Capture device: an ESP32-S3 with OV5640 is quoted at 640×480/40 fps and 1280×720/30 fps MJPEG ([espboards](https://www.espboards.dev/blog/esp32-camera-modules-compared/)), but a measured ESP32-CAM/OV2640 stream over Wi-Fi gives ~14 fps at VGA ([benchmark paper](https://pith.science/paper/2505.24081)); plan for VGA MJPEG at 15–20 fps and decode on the Mac.

## 8. What to measure first on the target Mac (the numbers above that are extrapolated)
1. EdgeTAM Core ML export vs sam2-mlx tiny at 512/768/1024 internal resolution, 1 vs 4 objects (this decides the frame rate).
2. YOLOE-26s Core ML (ANE) vs MLX at 640 and 480.
3. Hands23 on MPS at 800 px (decide whether to keep it or rely on keypoint geometry).
4. Qwen3-VL-4B 4-bit via mlx-vlm: 8 timestamped frames with prefix caching.
5. X3D-S vs VideoMAE-S on 16-frame crops via MPS.
